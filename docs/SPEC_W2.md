# SPEC W2: Event pipeline that survives a crash

**Done when:** the crash test (kill the worker mid-stream, restart it) loses nothing, processes nothing
twice, and its numbers are written up here.

## Topics

Redpanda (Kafka API) runs in compose; Redpanda Console is on <http://localhost:8080>. A one-shot
`redpanda-init` container creates the topics on startup (it is a no-op when they already exist).

| Topic | Partitions | Key | Producer | Consumer |
|---|---|---|---|---|
| `pr-events` | 3 | repo `full_name` | ingester outbox relay | worker (group `worker`) |
| `pr-events.dlq` | 1 | original key | worker | `scripts/dlq_replay.py` |

Keying by `repository.full_name` sends every event of one repo to the same partition, so the worker sees
a repo's events in the order the ingester accepted them. Different repos are processed in parallel.

Brokers: `redpanda:9092` inside the compose network, `localhost:19092` from the host
(`KAFKA_BOOTSTRAP_SERVERS`).

## Event envelope

Every message on `pr-events` is UTF-8 JSON of `shipwatch_common.kafka.EventEnvelope`:

| Field | Type | Meaning |
|---|---|---|
| `event_id` | UUID | Generated by the ingester when it accepts the delivery. The consumer's idempotency key. |
| `delivery_id` | str | GitHub's `X-GitHub-Delivery`, for tracing a message back to the webhook. |
| `type` | str | `<event>.<action>`, e.g. `pull_request.opened`. |
| `occurred_at` | datetime (UTC, ISO 8601) | When the ingester accepted the delivery. |
| `payload` | object | The GitHub payload, unchanged. |

```json
{"event_id": "0b6d…", "delivery_id": "72d3…", "type": "pull_request.opened",
 "occurred_at": "2026-11-02T10:00:00.123456Z", "payload": {"action": "opened", "…": "…"}}
```

## Transactional outbox

Publishing to Kafka straight after the DB commit has a gap: if the process dies, or Kafka is down,
between the commit and the publish, the delivery is stored (and GitHub got its 202, so it won't resend)
but never published. Publishing *before* the commit has the opposite gap (published, then rolled back).

So the ingester never talks to Kafka in the request path. In the **same transaction** that records the
delivery and upserts the PR, it inserts an `outbox` row holding the envelope. Either both commit or
neither does. A relay loop then copies outbox rows to Kafka.

```
outbox(id BIGINT IDENTITY PK, event_id UUID UNIQUE, topic, key, envelope JSONB,
       created_at, sent_at NULL, attempts INT, last_error TEXT)
-- partial index on id WHERE sent_at IS NULL: the relay's scan stays cheap as sent rows pile up
```

- Only `pull_request` deliveries get an outbox row. Ignored event types and duplicates don't (a duplicate
  rolls the whole transaction back).
- After the commit the endpoint wakes the relay and returns `202` immediately. It never waits on Kafka, so
  a Kafka outage doesn't fail webhooks.

### Relay

Runs as a background task inside each ingester process (started in the FastAPI lifespan).

1. Wait for a wake-up from the endpoint, or 0.5 s.
2. In one transaction: `pg_try_advisory_xact_lock(<relay lock id>)`. If another relay holds it, skip this
   round. One active relay at a time is what keeps a repo's events in order even with several ingester
   replicas (`SKIP LOCKED` workers would publish a repo's rows in parallel and could reorder them).
3. `SELECT … WHERE sent_at IS NULL ORDER BY id LIMIT 100`.
4. Produce all of them (`acks=all`, idempotent producer), then flush and collect each delivery report.
5. Set `sent_at = now()` on the rows **up to the first failure**. The failed row gets `attempts + 1` and
   `last_error`; it and every row after it stay unsent and are retried next round, so a failure never lets
   a later event of the same repo overtake an earlier one. Rows after the failure may already be in Kafka,
   so they are published again: delivery is **at-least-once** and consumers dedupe on `event_id`.
6. Commit.

On shutdown the loop stops and the producer is flushed. Unsent rows wait for the next start.

### Failure handling

| Failure | Result |
|---|---|
| Ingester crashes before the commit | Nothing stored, GitHub gets no 2xx. Redeliver to recover (see W1 TODO). |
| Ingester crashes after the commit, before publishing | Outbox row is unsent; the relay publishes it after restart. |
| Kafka down | Webhooks still get `202`; rows accumulate unsent with `attempts`/`last_error`, and drain in order once Kafka is back. |
| Relay crashes after publishing, before marking sent | Rows are published again on restart. Duplicate messages, same `event_id`. |
| Postgres down | `500` as in week 1; the outbox can't help, since it lives in Postgres. |

## Worker (`services/worker`)

Consumes `pr-events` in consumer group `worker` with `enable.auto.commit=false`.

```
loop:
    msg = poll()
    handle(msg)            # process, retrying; or dead-letter. Raises only if the DLQ is unreachable.
    commit(msg, sync)      # only now: a crash anywhere above means the message is redelivered
```

- **Processing (for now):** log the event and insert a `processed_events` row. Week 3 replaces this with
  the PR risk agent; the retry/DLQ/idempotency wrapper stays.
- **Graceful shutdown:** SIGTERM/SIGINT set a stop flag. The message in hand finishes (including its
  retries) and is committed, then the consumer closes. Compose gives it `stop_grace_period: 30s`.
- **Static group membership** (`CONSUMER_INSTANCE_ID`, `worker-1` in compose; found by the crash test):
  a SIGKILLed consumer can't leave the group, so with dynamic membership its partitions stayed frozen
  until its session timed out (45 s by default), and recovery took over 60 s. With a stable
  `group.instance.id` the restarted container rejoins as the same member and gets its partitions back
  at once. `session.timeout.ms` is also lowered to 10 s. The id must be unique per replica.

```
processed_events(event_id UUID PK, delivery_id, type, topic, partition, offset,
                 deliveries INT DEFAULT 1, processed_at)
```

## Retries and dead-letter queue

Retries happen in-process, so a partition doesn't advance while one of its messages is being retried.
That keeps a repo's events in order; the price is that one slow message stalls its partition (bounded:
3 attempts, backoff capped at 5 s).

| Error | Class | Handling |
|---|---|---|
| `TimeoutError`, `ConnectionError`/`OSError`, SQLAlchemy `OperationalError`, Redis errors, `InjectedFailure`, anything unexpected | retryable | up to `MAX_ATTEMPTS` (3) attempts, then DLQ |
| `pydantic.ValidationError` (bad envelope, not JSON), `JSONDecodeError`, `UnicodeDecodeError`, Postgres `DataError`/`IntegrityError` | non-retryable | DLQ at once (`attempts: 1`) |

Unknown errors count as retryable: a bug costs two extra attempts, while wrongly treating a transient
error as permanent would dead-letter good events.

**Backoff:** exponential with full jitter. Before attempt *n+1* wait `uniform(0, min(5 s, 0.5 s · 2^(n-1)))`.
The jitter keeps many consumers from retrying a recovering dependency in lockstep.

**Dead-letter record** on `pr-events.dlq`, keyed like the original:

```json
{"original": {"topic": "pr-events", "partition": 1, "offset": 42, "key": "octo/sandbox",
              "headers": {}, "value": {"event_id": "…"}, "value_encoding": "json"},
 "error": {"type": "TimeoutError", "message": "…", "retryable": true, "attempts": 3,
           "first_failed_at": "2026-11-04T10:00:00+00:00", "last_failed_at": "…"}}
```

`value_encoding` is `json` when the original bytes parsed as JSON, otherwise `base64` of the exact bytes.
The worker waits for the DLQ write to be acknowledged **before** committing. If the DLQ write fails, the
worker exits without committing (compose restarts it) and the message is redelivered: never lost.

**Fault injection:** `FAIL_RATE` (0–1) makes each attempt fail with an `InjectedFailure` with that
probability. `FAIL_RATE=1` sends everything to the DLQ.

## Idempotent processing

Kafka plus the outbox give at-least-once delivery, so the worker sees duplicates: the relay republishes
after a failure, a worker crash before commit redelivers, a DLQ replay resends. Processing must still
happen once per `event_id`.

Redis key `shipwatch:evt:<event_id>`:

1. `SET key processing:<token> NX EX 20` (the lease).
   - Set → we own it: process.
   - Exists with `done` → already processed: log, skip, commit.
   - Exists with `processing:…` → another attempt holds the lease, almost always one that crashed. Wait
     until the lease expires, then claim it.
2. After success: `SET key done EX 7d`.
3. After a failed attempt: delete the key if it still holds *our* token (compare-and-delete in Lua),
   so the retry, or a later DLQ replay, can claim it.
4. While an attempt runs, the lease is renewed every `lease / 3` (compare-and-`PEXPIRE`), so a slow but
   live attempt never loses it. Only a dead worker's lease runs out.

### Why a status key instead of `SET event_id NX` up front

Marking an event as seen *before* processing it means a crash mid-processing leaves the key behind and
every redelivery is skipped: the event is silently lost. Marking it only *after* processing means two
consumers (or a redelivery racing a slow attempt) can both process it. The two-state key splits the
difference: `processing` with a short lease blocks concurrent duplicates, and `done` with a long TTL
blocks later ones.

Trade-offs of the lease length (`PROCESSING_LEASE_SECONDS`, 20 s):

- **Too short:** without renewal, a slow but healthy attempt would outlive its lease and a redelivered
  copy would run alongside it (week 3's LLM calls easily take 20 s). Renewal removes this, so the lease
  only has to outlast a renewal hiccup, not the whole processing time.
- **Too long:** after a crash mid-message, that event's partition waits up to the full lease before the
  event is retried.
- **7-day `done` TTL:** a duplicate arriving after 7 days is no longer caught by Redis.

So Redis is a fast path, not the source of truth. `processed_events.event_id` is the primary key and the
insert is `ON CONFLICT DO UPDATE SET deliveries = deliveries + 1`, inside the processing transaction. A
duplicate that gets past Redis (the worker died after the Postgres commit but before `done`, the lease
expired, the key aged out, or Redis was down) bumps `deliveries` and changes nothing else. **If Redis is
unreachable the worker processes without the gate** and relies on the primary key; failing every event
into the DLQ during a Redis outage would be worse. Week 3's side effects (verdicts) must keep the same
rule: written in one transaction, keyed by `event_id`.

## Delivery guarantees

**At-least-once delivery, effectively-once processing.**

- *At-least-once:* an event accepted with `202` is in the outbox in the same transaction. The relay
  retries until Kafka acknowledges it (`acks=all`), and the worker commits an offset only after the
  message is processed or safely in the DLQ. Every failure is answered by sending again, never by
  dropping, so duplicates are possible and loss is not.
- *Effectively-once:* every copy of an event carries the same `event_id`. The Redis status key skips
  copies cheaply; the `processed_events` primary key makes the effect itself idempotent, in the same
  transaction as the effect. However many copies arrive, the effect is applied once.
- *Ordering:* per repo (Kafka key → one partition, one relay, in-process retries). Duplicates can
  re-deliver an old copy after a newer event (see review), so consumers mustn't treat "arrived later"
  as "is newer"; week 1's `updated_at` guard already does this for PR state.

| Failure | What happens | Lost? | Duplicated? |
|---|---|---|---|
| Ingester crashes before the DB commit | Transaction rolls back, GitHub gets no `2xx` | Only until redelivered from GitHub (W1 TODO: automatic reconcile) | No |
| Ingester crashes after the commit, before the relay publishes | Outbox row stays unsent; the next ingester start publishes it | No | No |
| Relay crashes after publishing, before marking rows sent | Rows republished on restart | No | Copies in Kafka; skipped by the worker |
| Kafka down | Webhooks still get `202`; outbox rows wait (`attempts`, `last_error`, backoff up to 10 s) and drain in order when Kafka is back | No | Possibly, if a batch partially failed |
| Worker crashes mid-message, before the DB commit | Offset not committed → redelivered; the dead attempt's lease expires (≤ 20 s), then it is processed | No | No |
| Worker crashes after the DB commit, before marking Redis `done` | Redelivered; lease expires; the PK catches it (`deliveries = 2`) | No | No (effect once) |
| Worker crashes after `done`, before the offset commit | Redelivered; Redis says `done` → skipped and committed | No | No |
| Transient error (timeout, connection) | Retried 3× with jittered backoff, then DLQ | No (DLQ + replay) | No |
| Poison message (bad JSON, invalid envelope, bad data) | Straight to DLQ (`attempts: 1`), committed, partition moves on | No (DLQ) | No |
| DLQ unreachable when dead-lettering | Worker exits without committing; compose restarts it; message redelivered | No | No |
| Redis down | Processes without the gate; the PK still dedupes | No | No (effect once) |
| Postgres down | Ingester `500` (W1 behaviour). Worker attempts fail as retryable → after 3 attempts, DLQ | No (DLQ + replay) | No |

### Crash test results

`scripts/crash_test.py` produces events with unique ids at a steady rate, `docker kill`s (SIGKILL) the
worker after a random 2–5 s, waits 3 s, starts it again, and counts once the backlog drains. The full
log is in [results/crash_test.md](results/crash_test.md).

| Run | Events | Killed at | Processed at kill | Processed | Duplicates | Lost | In DLQ | Took |
|---|---|---|---|---|---|---|---|---|
| 1 | 1,000 @ 100/s | 3.6 s | 365 | 1,000 | 0 | 0 | 0 | 10 s |
| 2 | 1,000 @ 100/s | 4.8 s | 482 | 1,000 | 0 | 0 | 0 | 11 s |
| 3 | 1,000 @ 100/s | 2.7 s | 273 | 1,000 | 0 | 0 | 0 | 10 s |
| extra: `--fail-rate 0.3` | 1,000 @ 100/s | 3.7 s | 31 | 976 | 0 | 0 | 24 | 142 s |
| extra: backlog | 3,000 @ 1,000/s | 2.8 s | 1,468 | 3,000 | 0 | 0 | 0 | 11 s |

- **Duplicates** = events whose processing reached the database more than once (`deliveries > 1`).
  Effects applied twice are impossible by the primary key, so this measures how often Redis alone
  wasn't enough.
- **Bug found and fixed:** the first paced run lost nothing but took 63 s. The killed member kept its
  partitions until its 45 s session timed out. Fix: static membership plus a 10 s session timeout
  (above); recovery is now immediate (runs 1–3 finish when production finishes, at ~10 s). There's a
  regression test for it (`test_static_member_takes_its_partitions_back_right_after_a_crash`).
- The `--fail-rate 0.3` run expects about 1000 × 0.3³ ≈ 27 events to fail all 3 attempts; 24 did, all in
  the DLQ, so `processed + in DLQ = produced`. It is slower because of the in-process backoff.
- **Limit:** in these runs the kill never landed in the few-millisecond window between processing a
  message and committing its offset (the worker logged exactly one `event processed` per event and no
  skips). Those paths are covered by integration tests instead: same event twice, crash between the DB
  commit and `done`, lease left by a crashed attempt.

## DLQ replay

`scripts/dlq_replay.py` lists the DLQ grouped by error type and republishes chosen messages to
`pr-events` with their original key and an `x-replayed-from: dlq/<partition>/<offset>` header. It reads
the whole DLQ without committing offsets, so listing is read-only. Usage: README → Operations.
